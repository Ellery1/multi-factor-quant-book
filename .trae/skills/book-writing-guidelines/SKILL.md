# 《量化之路-多因子的语言》写作规范

本skill适用于本书所有章节（含前言、附录、章末代码）的写作、修订与审查。当用户请求"补充某节内容"、"改写某段"、"加一个例子"、"加一个推导"等任何与本书正文相关的写作任务时，必须遵守以下规则。

## 一、预期读者画像（写作时时刻不忘）

本书的目标读者是：**具备本科数学水平的理工生，对投资很有兴趣，但没有投资的基础知识**。

推论：
- 数学：可以假设读者懂微积分、线性代数、概率统计的基础概念，但具体公式（如中心极限定理、t分布、协方差矩阵求逆）需要简要回顾
- 投资：所有投资术语（多空、对冲、beta、alpha、IC、IR、因子值vs因子收益、横截面、回测、调仓、融券）**首次出现必须解释**，不能默认读者懂
- 直觉优先：能用一句话的类比说清楚的概念，不要直接甩定义
- 不假设：读者不知道"PE是市盈率"、不知道"融券怎么操作"、不知道"调仓频率"是什么

## 二、四大核心写作原则（强制遵守）

### 原则1：先业务后数学（最重要）

引入任何数学模型、公式或推导时，必须遵循以下顺序：

1. **业务现状**：先描述投资实务中"现在大家是怎么做的"或"市场是怎么运作的"
2. **提出问题**：从业务现状中提炼出一个需要回答的精确问题
3. **引入数学模型和公式**：说明"为了回答上面的问题，我们引入XX模型"
4. **参数说明**：公式中每个符号都要解释含义和单位
5. **推导**：从假设到结论，一步一步来
6. **得出结论**：用自然语言陈述推导结果
7. **现实例子**：用一个具体的数字例子（最好是A股真实数据）说明结论如何回答了初始的业务问题

**反例（不可这样写）**：
> "IC定义为 Spearman(f_t, r_{t+1})。"

**正例**：
> "如果因子有效，因子值高的股票应该收益高。但光'应该'是不够的，我们需要一个数字来量化这种'关联强度'。这就引出了信息系数（IC）的概念。IC的本质是因子值与下期收益的Spearman秩相关系数……（公式）……参数说明……（手算实例）……"

### 原则2：语言风格——尽量少用破折号

- 破折号（——）能不用就不用，能改写就改写
- 用冒号、句号、括号或直接断句来替代
- 列表项的"含义解释"可以用冒号分隔，不要用破折号

**反例**：
> "因子A的IC均值是0.06——但稳定性极差——大起大落。"

**正例**：
> "因子A的IC均值是0.06，但稳定性极差，大起大落。"

### 原则3：专有名词前置解释

**任何专有名词在第一次出现前，必须先用自然语言解释清楚**。不解释就使用等于把读者丢下车。

- 投资术语（多空、对冲、beta、alpha、IC、IR、横截面、调仓、融券、做空、T+1）
- 统计术语（零假设、备择假设、p值、t统计量、置信区间、标准误、秩相关、自由度）
- 数学术语（协方差矩阵、特征值、正定、正交化、AR(1)、半衰期）
- 财务术语（TTM、净利润、净资产、ROE、PE、PB、股息率）

格式建议：在术语首次出现时，用括号或blockquote给出简短解释。

**正例**：
> "IC（信息系数，Information Coefficient）就是因子值与下期收益的Spearman秩相关系数。"

### 原则4：数据必须有出处

任何具体数字（百分比、相关系数、收益、IR、t值、半衰期、φ值、矩阵元素等）必须满足以下之一：

1. **引用文献**：在数字后加角标[1]，章末列出完整文献（含作者、年份、期刊、卷期页）
2. **自己写代码获取**：代码放在`book/code/`下，运行结果以json/csv形式保存，正文中注明"数据来源：基于tushare全A股XXXX-XXXX年数据，代码见`book/code/xxx.py`"

**绝对禁止**：编造数字当作真实数据使用。如果确实需要用示意性数字说明计算流程，必须明确标注"示意性数据，非真实"。

发现历史内容中存在编造数据时，应：
1. 立即在正文中加"⚠️ 示意性数据"标注
2. 在`book/待办事项.md`中登记，写明位置、当前数据、需要替换的真实数据要求

（开篇导语：1-2段，说明本章在整个体系中的位置和要解决的核心问题）

（正文）

## 四、📌 推导章节模板

凡是包含数学推导的小节，开头必须用 📌 模板，格式如下：

```markdown
### X.X.X 小节标题

> 📌 **本节要解决的问题**：用一句话描述业务或理论问题
>
> **我们的做法**：简述采用什么方法/模型来解决
>
> **得到的结论**：用自然语言陈述关键结论（不含公式）
>
> 以上是结论，以下为推导，读者可自行选择是否跳过该推导过程，继续阅读 X.X.X 节。

（推导正文）
```

模板要点：
- 先给结论，再给推导。读者可以选择只看结论跳过推导
- 结论部分不能出现公式，必须是纯自然语言
- "可跳过"提示要指明跳到哪里（下一小节编号）

## 五、参考文献角标规范

- 正文引用时用方括号上角标：`Grinold (1989)[1]`
- 角标紧跟作者或数字之后，不空格
- 章末参考文献按正文中首次出现顺序编号
- 文献格式：`[n] 作者, "论文标题," *期刊*, Vol.X, No.X, 年份, pp.X-X.`
- 书籍：`[n] 作者, *书名*, 出版社, 年份.`
- 同一文献在多章引用时，每章独立重新编号

## 六、公式规范

- 行内公式用 `$...$`，独占一行用 `$$...$$` 并带编号 `\tag{X.Y}`
- 公式编号格式：`(章号.序号)`，如 `\tag{5.11}`
- **关键**：`\tag{}`必须被`$$`完整包裹，否则会触发 LaTeX `#` 报错
- 公式后必须给出参数说明（bullet list 或正文）
- 复杂公式后必须给出"直观理解"或"读作"的自然语言解释

**正例**：
```latex
$$t = \frac{\overline{IC} \cdot \sqrt{T}}{s_{IC}} = IR \cdot \sqrt{T} \tag{5.11}$$

其中 $IR = \overline{IC} / s_{IC}$ 是信息比率，$T$ 是观测期数。
```

**反例**（会报错）：
```latex
$$t = \frac{\overline{IC} \cdot \sqrt{T}}{s_{IC}} \tag{5.11}$
```

## 七、术语统一规范

本书统一以下术语用法，避免歧义：

| 推荐用法 | 避免用法 | 原因 |
|---------|---------|------|
| 低估值 | 便宜、便宜货 | "便宜"歧义（价格低还是估值低？） |
| 估值偏高 | 贵 | 同上 |
| 因子值 | 因子 | "因子"既可指指标也可指收益率，需区分 |
| 因子收益率 | 因子回报 | 统一术语 |
| 多头/空头 | 做多/做空 | 在分层回测语境中统一用"多/空" |
| 多空收益 | 价差收益 | 统一术语 |
| 零假设 | 原假设 | 统一术语 |
| Spearman秩相关 | 秩相关系数 | 明确指定 |
| A股 | 中国股市 | 标准简称 |

## 八、例子与Worked Example规范

- 每个核心公式后必须配一个具体的数字例子（"Worked Example"）
- 例子优先用A股真实数据（如沪深300成分股、2024年某月数据）
- 例子要完整：给出输入、计算过程、最终结果
- 计算过程要清晰展开，避免"跳步"
- 真实数据需注明来源；示意数据需标注"非真实数据/示意性"

## 九、待办事项登记规范

发现以下情况时，必须在 `book/待办事项.md` 中登记：

1. 正文中使用了编造/示意数据
2. 引用了文献但未列出完整出处
3. 某段推导不完整或存疑
4. 某个数据点需要tushare或其它数据源核实

登记格式：
```markdown
### 事项X：简述问题

**位置**：`book/partX-XXX/chYY-XXX.md` §X.X.X

**当前内容**：（引用当前正文）

**需要做的**：
1. ...
2. ...

**数据来源**：tushare / 文献引用 / 其他
```

## 十、Git操作规范

- 所有git操作（commit、push、add等）必须经用户明确同意后才能执行
- 不要主动运行git commit，除非用户说"提交"或"推代码"
- 推送失败时不要反复重试，告知用户让其手动处理
- HTML文件在markdown修改后重新生成，命名为`量化之路-多因子的语言.html`

## 十一、审查清单（修订章节时逐条对照）

修订任何章节时，完成修订后应逐条核对：

- [ ] 每个数学模型是否按"业务现状→问题→模型→参数→推导→结论→例子"的顺序展开？
- [ ] 是否有破折号可以替换为其他标点？
- [ ] 所有首次出现的专有名词是否都先给出了解释？
- [ ] 所有具体数字是否有出处（文献角标或代码数据来源）？
- [ ] 是否有编造数据未标注"示意性"？
- [ ] 推导章节是否使用了📌模板？
- [ ] 公式是否完整包裹在`$$...$$`中，`\tag{}`没有溢出？
- [ ] 章末是否有参考文献节（如有引用）？
- [ ] 是否有计算例子支撑核心公式？
- [ ] 术语是否统一（低估值而非便宜，零假设而非原假设等）？

## 十二、适用范围与例外

本规范适用于：
- 所有正文章节
- 前言与README
- 附录

例外：
- 代码文件（`book/code/*.py`）中的注释不受本规范约束，但代码本身应有清晰的docstring
- 章末"Python验证代码"段中的代码块不受本规范约束，但其计算结果在正文引用时仍需遵守数据出处规范
- 待办事项、build脚本等工程性文件不受本规范约束
